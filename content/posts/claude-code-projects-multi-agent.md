你正在用 Claude Code 开发一个项目。它负责修改页面，你又想同时检查数据库设计、梳理接口文档、排查测试问题。

最直接的办法，是再打开几个 Claude 会话：一个处理前端，一个检查后端，一个负责测试。但很快，新的问题出现了：哪个会话在工作，哪个正在等确认？两个 Agent 会不会修改同一个文件？某个任务完成后，谁来检查并整合结果？你离开电脑后，如何知道项目卡在哪一步？

这些问题的核心，已经不是“AI 能不能写代码”，而是**人如何管理多个同时工作的 AI**。

Claude Code Projects 提供了一种思路：让一个协调者负责理解目标、拆分工作和汇总结果，再由多个线程分别执行具体任务。

## 一、从“开多个窗口”，变成“管理一个项目”

在普通使用方式下，你可能会开三个独立会话：一个修改用户登录页面，一个检查登录接口，另一个补充登录功能文档。每个会话都能工作，但你需要自己记住它们的状态，并在必要时传递信息。

按照 Anthropic 的介绍，Claude Code Projects 的思路是把这些工作放到一个项目中，由一个**协调者（Coordinator）**接收目标，再分派给不同的工作线程。[1]

```text
你：完善用户登录功能
          │
          ▼
     项目协调者
      /   |   \
     ▼    ▼    ▼
  前端  接口  文档
  线程  线程  线程
      \   |   /
          ▼
    汇总结果和问题
```

协调者更像一个项目助理：它需要决定工作怎么拆、由谁处理、哪些结果需要你查看。这不意味着它必然能正确拆分所有任务，也不意味着最终结果无需审查。它的价值在于**减少人工在多个会话之间切换和传话的负担**。

## 二、协调者与线程各做什么？

可以把两者的关系理解成“负责人”和“执行者”。

### 协调者：理解目标与组织工作

用户不一定要预先写好完整的任务清单。例如，你可以提出：

> 检查预约流程目前有哪些问题，先分析，再给我一个修复方案。

协调者可以根据项目上下文，考虑是否需要同时检查前端表单、后端接口和现有测试。理想情况下，它还应该向用户说明发现了什么、哪些地方需要决策。

但要注意：**能自动拆解，不代表可以跳过授权。**如果任务涉及数据库迁移、线上发布、支付或删除数据，仍应明确规定哪些动作必须先询问用户。

### 工作线程：处理具体任务

根据 Anthropic 的官方介绍，每个线程都是一个 Claude Code 云会话，使用各自的代码分支和仓库副本。[1]

例如：线程 A 检查预约页面的字段校验；线程 B 分析预约接口的错误处理；线程 C 阅读已有测试，整理缺口。

线程完成后，协调者再汇总结果。用户也可以进入某个线程，查看细节或调整方向。

这种隔离有利于并行工作，但**隔离不等于绝不会冲突**。如果两个线程都修改了同一段代码，合并时仍可能产生 Git 冲突，需要解决后才能安全整合。[1]

## 三、并行开发解决了什么，又带来了什么？

### 适合并行的任务

如果多个任务相互独立，并行通常更容易发挥价值：

| 任务 | 能否相对独立 |
|---|---|
| 检查前端页面文案 | 可以 |
| 整理 API 文档 | 可以 |
| 审查现有代码安全问题 | 可以 |
| 修改同一个数据库表和相关接口 | 需要协调依赖 |
| 同时改动同一个组件 | 容易发生冲突 |

例如，三个 Agent 分别阅读前端、后端和文档，再汇总问题，通常比让它们同时重写一个文件更容易控制。

### 不适合盲目并行的任务

并行并不是越多越好。如果任务依赖前一步结果，就不应该强行同时推进。

```text
先确定数据库字段
       ↓
再修改后端接口
       ↓
最后调整前端页面
```

如果字段还没确定，就让前后端 Agent 各自开工，可能分别采用不同的字段名，最后增加返工。因此，**好的多 Agent 协作，重点不只是并行，而是分清哪些能并行、哪些必须等待。**

## 四、它和 Hermes Kanban Swarm 有什么区别？

本博客此前介绍过 Hermes Kanban Swarm。两者都涉及多 Agent 协作，但关注点不同。

| 维度 | Claude Code Projects | Hermes Kanban Swarm |
|---|---|---|
| 用户入口 | 在项目会话中描述目标、查看线程 | 通过看板任务组织工作 |
| 工作组织 | 协调者分派和汇总项目线程 | 创建有依赖关系的任务图 |
| 主要关注 | 项目会话、代码任务和进度交互 | 看板任务、依赖关系及执行状态 |
| 结果整合 | 协调者汇总；代码可能通过分支和 PR 整合 | 由任务依赖串联 worker、验证与汇总 |
| 需要注意 | 并行修改仍可能产生合并冲突 | 任务状态流转不等于内容一定正确 |

这里不宜简单判断“谁更先进”。它们面向的工作方式不同：前者侧重一个项目中的协调体验；后者侧重把工作拆成可跟踪的任务图。

例如，写一篇博客时，你可以让不同 Agent 分别调研、写作、审核；开发一个仓库时，也可以让多个线程检查不同模块。**无论采用哪种方式，都需要有人定义验收标准。**

有关 Hermes Kanban Swarm 的具体实现，可以参考本站已有的[深度解析文章](https://xueke9417-a11y.github.io/Hermes-blog/posts/hermes-kanban-swarm/)。

## 五、如果用在个人项目，怎么控制风险？

以一个预约服务项目为例，与其只说“继续开发”，不如给协调者明确边界：

> 请先检查当前项目状态，整理已经完成、正在进行和暂缓的功能。给出下一步建议，但先不要修改代码。数据库迁移、安装依赖、运行完整测试和发布操作，必须先征求我的同意。

这类指令包含了四个关键点：**当前目标**是先查清项目状态；**预期产出**是给出下一步建议；**操作边界**是先不要修改代码；**人工确认点**是高风险操作必须先问。

如果进入实际开发，还可以给每个线程限定范围。例如，让一个线程只读前端代码，另一个只检查接口，第三个整理测试建议。这样能降低多个 Agent 互相覆盖的风险。

另外，即使 Agent 反馈“测试通过”，也要区分：是它实际运行了测试，还是引用旧结果？测试是否会修改本地数据库？测试覆盖的是整个产品，还是当前部分功能？提交到了本地 Git，还是已经推送到远程？这些判断不会因为有了协调者就自动消失。

## 六、能在手机上远程管理吗？

Anthropic 的官方介绍提到，用户可以通过手机查看和引导项目进展。[1] 这对需要暂时离开电脑的开发者有吸引力：AI 在执行，用户只在需要判断的时候介入。

但需要区分两件事：**查看云端项目线程**，与控制电脑上正在运行的现有 VS Code 会话，不一定是同一种能力；功能是否可用，还取决于账号资格、客户端、项目配置和当前开放范围。

官方文章发布于 **2026 年 9 月 17 日**，当时说明新项目体验处于 Beta，面向符合条件的用户逐步开放。[1] 本文撰写时，没有实测特定用户账号是否具备该功能，也没有验证它能否接管现有的 VS Code 会话。

## 结语：真正重要的是管理边界，而不是 Agent 数量

Claude Code Projects 展示了一种更自然的多 Agent 工作方式：用户提出目标，协调者安排线程，线程分别完成工作，再将结果和问题带回主会话。

但项目能否安全推进，仍取决于几个基本问题：任务是否拆得合理；多个线程是否会互相覆盖；结果有没有被实际验证；高风险操作是否保留人工确认；用户能否看清进度和阻塞。

未来，开发者可能不只是“让 AI 写一段代码”，还要学会**给多个 AI 分工、设置边界、检查结果**。协调工具可以减少管理负担，但不能替代对项目的判断和责任。
